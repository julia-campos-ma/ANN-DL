    4. VAE

    Enunciado

    Exercises → VAE

    Visão geral

    O exercício treina um autoencoder variacional (VAE; KINGMA; WELLING, 2014; REZENDE; MOHAMED; WIERSTRA, 2014) no MNIST e estuda o equilíbrio entre reconstruir bem cada imagem e manter o espaço latente perto de uma priori da qual se possa amostrar. Os dois exercícios usam um único módulo, code/vae.py, com os dados, o modelo, a perda e o laço de treino. O Exercício 1 usa \(d = 16\) dimensões latentes; o Exercício 2 usa o mesmo código com \(d = 2\), o que só muda um argumento.

    Regras seguidas:

    • Sementes: torch.manual_seed(42) imediatamente antes de construir cada modelo (dentro de train_vae), e um torch.Generator com semente 42 no random_split. As avaliações usam um gerador próprio, com semente fixa, para não consumir o gerador do treino. Rodando os scripts duas vezes, os números saem idênticos.
    • Bibliotecas: torch, torchvision (só para carregar o MNIST), numpy, matplotlib, scipy (norm.ppf, item 2C). O scikit-learn não foi necessário: o k-NN usado apenas na análise 2E é escrito à mão em torch (knn_predict).
    • Partes do VAE escritas à mão: a reparametrização (reparameterize), os dois termos da perda (vae_loss_terms, com a KL em forma fechada escrita termo a termo) e a amostragem da priori (torch.randn). Nenhuma classe pronta de VAE e nenhum torch.distributions. O autograd calcula os gradientes.
    • Unidades: os dois termos da perda são sempre reportados separados, em nats por imagem (somados nos 784 pixels ou nas \(d\) dimensões e tirada a média sobre as imagens).
    • Teste só no fim: todos os hiperparâmetros são fixados pelo enunciado, então nenhuma decisão de treino foi tomada; a validação serve para acompanhar o treino. O conjunto de teste só é avaliado com cada modelo já treinado (depois das 20 épocas), para os números finais.

    """VAE para o MNIST: dados, modelo, perda e laço de treino (PyTorch).

Este módulo é o "núcleo" usado pelos dois exercícios:

    * Exercício 1 — VAE com espaço latente de dimensão d = 16;
    * Exercício 2 — o MESMO modelo, os mesmos dados, a mesma semente, o mesmo β e o
      mesmo orçamento de treino, só que com d = 2.

As partes próprias do VAE são escritas à mão, como pede o enunciado: o truque da
reparametrização (``reparameterize``), os dois termos da perda (``vae_loss_terms``, com a
KL em forma fechada) e a amostragem da priori (feita nos scripts com ``torch.randn``).
O autograd do PyTorch calcula os gradientes; não usamos nenhuma classe pronta de VAE nem
``torch.distributions``.

Notação (a mesma da aula):

    q_φ(z | x) = N(μ_φ(x), diag σ²_φ(x))     codificador (encoder)
    p(z)       = N(0, I)                      priori
    p_θ(x | z) = Bernoulli(x̂_θ(z))            decodificador (decoder), x̂ ∈ (0, 1)^784

    −ELBO(x) = E_q[−log p_θ(x | z)]  +  β · KL(q_φ(z | x) ‖ p(z)),   β = 1
               └── reconstrução (BCE) ┘    └─────── KL ───────┘

Os dois termos são reportados SEPARADAMENTE, em nats por imagem: somados nos 784 pixels
(ou nas d dimensões, no caso da KL) e depois tirada a média sobre as imagens.
"""

from pathlib import Path

import torch
import torch.nn as nn
import torch.nn.functional as F
from torch.utils.data import DataLoader, TensorDataset, random_split
from torchvision import datasets, transforms

REPO = Path(__file__).resolve().parents[4]   # raiz do repositório
DATA_DIR = REPO / "data"                     # o MNIST é baixado em data/MNIST (fora do git)
FIGURES = Path(__file__).resolve().parents[1] / "figures"
RESULTS = Path(__file__).resolve().parents[1] / "results"   # números em JSON

# Hiperparâmetros fixados pelo enunciado (item 1C)
SEED = 42
LR = 1e-3
BATCH_SIZE = 128
EPOCHS = 20
BETA = 1.0

# Paleta usada nas figuras (a mesma dos exercícios anteriores).
NAVY = "#173F5F"
PINK = "#D6336C"

# --------------------------------------------------------------------------------- dados
def load_mnist():
    """Item 1A: carrega o MNIST com pixels em [0, 1], achatados em vetores de 784.

    Devolve três ``TensorDataset`` (treino, validação, teste) com pares (x, rótulo).
    As 60 000 imagens oficiais de treino são divididas em 50 000 de treino e 10 000 de
    validação por ``random_split`` com um gerador de semente 42. As 10 000 imagens
    oficiais de teste formam o conjunto de teste e só são usadas nos números finais.
    """
    train_full = datasets.MNIST(DATA_DIR, train=True, download=True)
    test = datasets.MNIST(DATA_DIR, train=False, download=True)

    # data: uint8 (N, 28, 28) em {0..255}. Dividir por 255 dá exatamente o mesmo
    # resultado de transforms.ToTensor(), só que de uma vez para o conjunto inteiro.
    def to_dataset(ds):
        x = ds.data.reshape(-1, 784).float() / 255.0
        # Conferência: igual, pixel a pixel, ao ToTensor() aplicado imagem a imagem.
        assert torch.equal(transforms.ToTensor()(ds[0][0]).reshape(784), x[0])
        return TensorDataset(x, ds.targets.clone())

    full = to_dataset(train_full)
    train, val = random_split(full, [50_000, 10_000],
                              generator=torch.Generator().manual_seed(SEED))
    return train, val, to_dataset(test)


def stack(subset):
    """Junta um Dataset/Subset inteiro em dois tensores (X, y), na ordem original."""
    if isinstance(subset, TensorDataset):
        return subset.tensors
    x, y = subset.dataset.tensors
    idx = torch.as_tensor(subset.indices)
    return x[idx], y[idx]


# -------------------------------------------------------------------------------- modelo
class VAE(nn.Module):
    """Codificador 784 → 512 → 256 (ReLU), cabeças μ e log σ² (256 → d) e
    decodificador d → 256 → 512 → 784 (ReLU nas ocultas, sigmoide na saída)."""

    def __init__(self, latent_dim=16):
        super().__init__()
        self.latent_dim = latent_dim
        self.encoder = nn.Sequential(
            nn.Linear(784, 512), nn.ReLU(),
            nn.Linear(512, 256), nn.ReLU(),
        )
        self.mu_head = nn.Linear(256, latent_dim)       # μ_φ(x)
        self.logvar_head = nn.Linear(256, latent_dim)   # log σ²_φ(x)
        self.decoder = nn.Sequential(
            nn.Linear(latent_dim, 256), nn.ReLU(),
            nn.Linear(256, 512), nn.ReLU(),
            nn.Linear(512, 784), nn.Sigmoid(),          # x̂ ∈ (0, 1): médias de Bernoulli
        )

    def encode(self, x):
        """Devolve os parâmetros da posteriori aproximada q_φ(z | x)."""
        h = self.encoder(x)
        return self.mu_head(h), self.logvar_head(h)

    def decode(self, z):
        """Devolve x̂ = E[x | z], a probabilidade de cada pixel estar "aceso"."""
        return self.decoder(z)

    def forward(self, x, generator=None):
        mu, logvar = self.encode(x)
        z = reparameterize(mu, logvar, generator)
        return self.decode(z), mu, logvar


def reparameterize(mu, logvar, generator=None):
    """Truque da reparametrização: z = μ + σ ⊙ ε, com ε ~ N(0, I).

    Toda a aleatoriedade fica em ε, que não depende dos parâmetros. Assim z é uma função
    determinística e diferenciável de (μ, log σ²): ∂z/∂μ = 1 e ∂z/∂log σ² = ½ σ ε, e o
    gradiente passa pela amostragem (KINGMA; WELLING, 2014). Prever log σ² em vez de σ
    deixa a cabeça livre em (−∞, +∞) e garante σ = exp(½ log σ²) > 0.
    """
    std = torch.exp(0.5 * logvar)                                         # σ
    eps = torch.randn(mu.shape, generator=generator, dtype=mu.dtype)      # ε ~ N(0, I)
    return mu + std * eps


def vae_loss_terms(x, x_hat, mu, logvar):
    """Os dois termos da −ELBO, em nats por imagem (média sobre o lote).

    Reconstrução: −log p_θ(x | z) para um decodificador Bernoulli é a entropia cruzada
    binária SOMADA nos 784 pixels. ``reduction="sum"`` soma no lote todo; dividir pelo
    tamanho do lote dá a média por imagem. (Com ``reduction="mean"`` a BCE seria dividida
    também por 784, o que equivale a usar β ≈ 784 na KL.)

    KL em forma fechada entre N(μ, σ²) e N(0, 1), somada nas d dimensões latentes:

        KL = ½ Σ_j (μ_j² + σ_j² − 1 − log σ_j²)

    escrita termo a termo abaixo, sem ``torch.distributions``.
    """
    batch = x.shape[0]
    recon = F.binary_cross_entropy(x_hat, x, reduction="sum") / batch
    kl_per_image = 0.5 * (mu.pow(2) + logvar.exp() - 1.0 - logvar).sum(dim=1)
    kl = kl_per_image.mean()
    return recon, kl


# ------------------------------------------------------------------------------- treino
@torch.no_grad()
def evaluate(model, x, y=None, batch_size=1000, seed=123):
    """Reconstrução e KL médias (nats/imagem) num conjunto inteiro, sem atualizar pesos.

    O termo de reconstrução é estimado com UMA amostra z ~ q(z | x) por imagem (estimador
    não enviesado de E_q[−log p(x | z)]). As amostras de ε usam um gerador próprio, com
    semente fixa, para que a avaliação seja reprodutível e não consuma o gerador global
    usado no treino.
    """
    model.eval()
    gen = torch.Generator().manual_seed(seed)
    tot_rec = tot_kl = 0.0
    for i in range(0, len(x), batch_size):
        xb = x[i:i + batch_size]
        x_hat, mu, logvar = model(xb, generator=gen)
        rec, kl = vae_loss_terms(xb, x_hat, mu, logvar)
        tot_rec += rec.item() * len(xb)
        tot_kl += kl.item() * len(xb)
    model.train()
    return tot_rec / len(x), tot_kl / len(x)


def train_vae(latent_dim, train_set, val_set, epochs=EPOCHS, verbose=True):
    """Itens 1C / 2A: treina um VAE e registra os dois termos por época.

    Adam (lr = 1e-3), lotes de 128, 20 épocas, β = 1. Em cada época guardamos:
      * no TREINO, a média dos termos ao longo da época (o modelo muda durante a época);
      * na VALIDAÇÃO, os termos com o modelo do fim da época.
    Também guardamos a validação ANTES do treino (época 0), usada na análise 1E.
    """
    torch.manual_seed(SEED)                                   # (semente antes do modelo)
    model = VAE(latent_dim)
    opt = torch.optim.Adam(model.parameters(), lr=LR)
    loader = DataLoader(train_set, batch_size=BATCH_SIZE, shuffle=True)
    x_val, _ = stack(val_set)

    history = {"train_rec": [], "train_kl": [], "val_rec": [], "val_kl": []}
    history["val_epoch0"] = evaluate(model, x_val)

    for epoch in range(1, epochs + 1):
        sum_rec = sum_kl = 0.0
        n_seen = 0
        for xb, _ in loader:
            x_hat, mu, logvar = model(xb)                     # forward com z reparametrizado
            rec, kl = vae_loss_terms(xb, x_hat, mu, logvar)
            loss = rec + BETA * kl                            # −ELBO média do lote
            opt.zero_grad()
            loss.backward()                                   # autograd passa por z = μ + σε
            opt.step()
            sum_rec += rec.item() * len(xb)
            sum_kl += kl.item() * len(xb)
            n_seen += len(xb)

        val_rec, val_kl = evaluate(model, x_val)
        history["train_rec"].append(sum_rec / n_seen)
        history["train_kl"].append(sum_kl / n_seen)
        history["val_rec"].append(val_rec)
        history["val_kl"].append(val_kl)
        if verbose:
            print(f"d={latent_dim:2d} época {epoch:2d} | treino: rec {sum_rec / n_seen:7.2f} "
                  f"KL {sum_kl / n_seen:6.2f} | val: rec {val_rec:7.2f} KL {val_kl:6.2f}")
    model.eval()
    return model, history


def checkpoint_path(latent_dim):
    """Onde os scripts guardam o modelo treinado (pasta fora do git, ver .gitignore)."""
    return Path(__file__).resolve().parents[1] / "checkpoints" / f"vae_d{latent_dim}.pt"


def get_trained_vae(latent_dim, train_set, val_set):
    """Carrega o modelo salvo pelo script do exercício; se não existir, treina de novo.

    Como o treino é determinístico (sementes fixas), treinar de novo dá o mesmo modelo;
    o arquivo salvo só evita repetir o treino quando o Ex. 2 precisa do modelo d = 16.
    """
    path = checkpoint_path(latent_dim)
    if path.exists():
        model = VAE(latent_dim)
        model.load_state_dict(torch.load(path))
        model.eval()
        return model, None
    model, history = train_vae(latent_dim, train_set, val_set)
    path.parent.mkdir(exist_ok=True)
    torch.save(model.state_dict(), path)
    return model, history

    B — Build the model

    Arquitetura (função VAE em vae.py):

    Bloco Camadas Ativação
    Codificador \(784 \to 512 \to 256\) ReLU depois de cada camada
    Cabeça \(\boldsymbol\mu\) \(256 \to d\) linear
    Cabeça \(\log\boldsymbol\sigma^2\) \(256 \to d\) linear
    Decodificador \(d \to 256 \to 512 \to 784\) ReLU nas ocultas, sigmoide na saída

    Com \(d = 16\), o modelo tem 1 079 600 parâmetros. O codificador define a posteriori aproximada \(q_\phi(\mathbf{z} \mid \mathbf{x}) = \mathcal{N}(\boldsymbol\mu_\phi(\mathbf{x}),\ \operatorname{diag}\boldsymbol\sigma^2_\phi(\mathbf{x}))\); a priori é \(p(\mathbf{z}) = \mathcal{N}(\mathbf{0}, \mathbf{I})\); o decodificador devolve \(\hat{\mathbf{x}} = D_\theta(\mathbf{z}) \in (0, 1)^{784}\), a probabilidade de cada pixel estar aceso, isto é, \(p_\theta(\mathbf{x} \mid \mathbf{z}) = \prod_j \text{Bernoulli}(x_j;\ \hat{x}_j)\).

    Reparametrização. Para que o gradiente passe pela amostragem, \(\mathbf{z}\) é escrito como uma função determinística de \((\boldsymbol\mu, \log\boldsymbol\sigma^2)\) e de um ruído que não depende dos parâmetros:

    \[ \mathbf{z} = \boldsymbol\mu + \boldsymbol\sigma \odot \boldsymbol\epsilon,\qquad \boldsymbol\epsilon \sim \mathcal{N}(\mathbf{0}, \mathbf{I}),\qquad \boldsymbol\sigma = \exp\!\left(\tfrac12 \log\boldsymbol\sigma^2\right), \]

    com \(\partial z_j/\partial\mu_j = 1\) e \(\partial z_j/\partial\log\sigma_j^2 = \tfrac12\sigma_j\epsilon_j\). A cabeça prevê \(\log\sigma^2\) (sem restrição de sinal) e não \(\sigma\), o que garante \(\sigma > 0\).

    Perda. Para cada imagem, a perda é a \(-\)ELBO com \(\beta = 1\):

    \[ \mathcal{L}(\mathbf{x}) = \underbrace{-\sum_{j=1}^{784}\Big[x_j\log\hat{x}_j + (1 - x_j)\log(1 - \hat{x}_j)\Big]}_{\text{reconstrução (BCE)} \;=\; -\log p_\theta(\mathbf{x}\mid\mathbf{z})} \;+\; \beta\,\underbrace{\frac12\sum_{k=1}^{d}\left(\mu_k^2 + \sigma_k^2 - 1 - \log\sigma_k^2\right)}_{\mathrm{KL}(q_\phi(\mathbf{z}\mid\mathbf{x})\,\|\,p(\mathbf{z}))}, \]

    com \(\hat{\mathbf{x}} = D_\theta(\mathbf{z})\) e \(\mathbf{z}\) reparametrizado, e a média é tirada sobre o lote. No código, a reconstrução é F.binary_cross_entropy(x_hat, x, reduction="sum") / batch. Com reduction="mean", a BCE seria dividida também por 784, o que equivale a multiplicar a KL por \(\beta \approx 784\) e esmagar o espaço latente.

    De onde vem a KL em forma fechada. Em uma dimensão, com \(q = \mathcal{N}(\mu, \sigma^2)\) e \(p = \mathcal{N}(0, 1)\):

    \[ \mathrm{KL}(q\,\|\,p) = \mathbb{E}_q[\log q(z) - \log p(z)] = \underbrace{-\tfrac12\log(2\pi\sigma^2) - \tfrac12}_{\mathbb{E}_q[\log q]} \;+\; \underbrace{\tfrac12\log 2\pi + \tfrac12(\mu^2 + \sigma^2)}_{-\mathbb{E}_q[\log p]} = \tfrac12\left(\mu^2 + \sigma^2 - 1 - \log\sigma^2\right), \]

    usando \(\mathbb{E}_q[(z - \mu)^2] = \sigma^2\) e \(\mathbb{E}_q[z^2] = \mu^2 + \sigma^2\). Como a covariância é diagonal, a KL em \(d\) dimensões é a soma das \(d\) parcelas. No código: 0.5 * (mu.pow(2) + logvar.exp() - 1.0 - logvar).sum(dim=1).

    E — Analysis

    1. A KL sobe nas primeiras épocas enquanto a perda total cai. Por que o otimizador escolhe pagar mais KL?

    A KL média é o custo, em nats, da informação que o código \(\mathbf{z}\) carrega sobre \(\mathbf{x}\): ela é um limite superior da informação mútua entre \(\mathbf{x}\) e \(\mathbf{z}\) (HOFFMAN; JOHNSON, 2016; ALEMI et al., 2018). Na inicialização, as cabeças devolvem \(\boldsymbol\mu \approx \mathbf{0}\) e \(\log\boldsymbol\sigma^2 \approx \mathbf{0}\), ou seja, \(q(\mathbf{z}\mid\mathbf{x}) \approx p(\mathbf{z})\) para toda imagem: medimos KL = 0,03 nats na validação antes do treino. Nesse ponto \(\mathbf{z}\) não diz nada sobre \(\mathbf{x}\), e o decodificador só pode devolver ≈ 0,5 em todos os pixels: a reconstrução vale 544,70 nats, praticamente \(784 \ln 2 = 543{,}4\).

    Treinar é "comprar" informação: afastar as posterioris da priori (mover \(\boldsymbol\mu\) e encolher \(\boldsymbol\sigma\)) custa KL, mas permite ao decodificador saber qual imagem reconstruir. No começo a troca é muito vantajosa: da época 0 para a 1, a KL de validação sobe 13,5 nats e a reconstrução cai 414,5 nats. Como a perda soma os dois termos com \(\beta = 1\), o otimizador aceita pagar KL enquanto cada nat de KL comprar mais de um nat de reconstrução. A vantagem vai diminuindo: da época 1 para a 2, +2,5 nats de KL compram −22,4 de reconstrução; da época 10 para a 20, +1,2 compram só −4,9. Por isso a KL sobe rápido e depois quase estabiliza em ≈ 20 nats, enquanto a soma cai em todas as épocas (de 143,7 para 101,6 na validação). A KL por dimensão mostra como essa informação é distribuída: 12 das 16 dimensões são ativas (variância de \(\mu_k\) entre imagens maior que 0,01; BURDA; GROSSE; SALAKHUTDINOV, 2016), com 0,6 a 2,5 nats cada, e 4 ficam inativas, com KL ≈ 0,001: nelas a posteriori continua igual à priori, porque o ganho de reconstrução não pagaria o custo.

    2. Por que a Figura 3 parece pior que a Figura 2? Duas razões distintas.

    (a) Onde as amostras da priori caem. A Figura 2 decodifica \(\boldsymbol\mu\) de imagens reais, que caem onde o decodificador foi treinado. Na Figura 3, o \(\mathbf{z}\) vem da priori, mas o decodificador só viu códigos vindos da posteriori agregada \(q(\mathbf{z}) = \frac{1}{N}\sum_i q(\mathbf{z}\mid\mathbf{x}_i)\), e as duas não coincidem. Elas até têm os mesmos momentos de segunda ordem: a variância de \(q(\mathbf{z})\) por dimensão fica entre 0,97 e 1,08. Mas cada posteriori é estreita (\(\sigma\) médio de 0,22 nas dimensões ativas, contra 1 da priori), e 50 000 gaussianas estreitas não preenchem uniformemente a bola da priori em 12 dimensões: sobram buracos entre elas. Medimos isso diretamente. Pela priori, as 64 amostras da Figura 3 e 2000 códigos \(\mathbf{z} \sim q(\mathbf{z}\mid\mathbf{x})\) de imagens de teste são igualmente prováveis (mediana de \(\log p(\mathbf{z})\): −22,49 contra −22,40). Pela posteriori agregada, não: a mediana de \(\log q(\mathbf{z})\) é −52,9 para as amostras da priori e −32,6 para os códigos de teste, uma densidade cerca de \(e^{20} \approx 7 \times 10^{8}\) vezes menor. 27% das amostras da priori (17 de 64) ficam abaixo do percentil 5 dos códigos de teste, e a distância mediana ao \(\boldsymbol\mu\) de treino mais próximo (nas dimensões ativas) é 1,75, contra 1,21 para imagens de teste. O decodificador é chamado a extrapolar para regiões que quase nunca viu, e é aí que aparecem os dígitos híbridos e mal formados.

    (b) O que o decodificador devolve para um \(\mathbf{z}\). Mesmo num \(\mathbf{z}\) "bom", o decodificador não devolve uma imagem: devolve \(\hat{\mathbf{x}} = \mathbb{E}[\mathbf{x}\mid\mathbf{z}]\), a probabilidade de cada pixel estar aceso, com os pixels independentes entre si. Se um mesmo \(\mathbf{z}\) é compatível com várias imagens (um traço um pouco mais à esquerda ou à direita, o alto do "4" aberto ou fechado), a melhor resposta para a BCE é a média delas, que é uma imagem borrada, com traços em meia-tinta (a KL é mode-covering e a média de vários modos é cinzenta). Essa incerteza é maior justamente onde \(\mathbf{z}\) é ambíguo, nas regiões entre classes e nos buracos do item (a). Medimos a fração de pixels "cinzentos" (\(0{,}1 < x < 0{,}9\)): 8,6% nas imagens de teste, 14,4% nas reconstruções a partir de \(\boldsymbol\mu\) e 16,7% nas amostras da Figura 3. Além disso, a figura mostra as médias \(\hat{\mathbf{x}}\) e não amostras de Bernoulli; sortear os pixels independentemente produziria ruído "sal e pimenta", porque o modelo não tem como representar a correlação entre pixels vizinhos de um traço.

    3. Por que decodificar \(\boldsymbol\mu\) em vez de um \(\mathbf{z}\) sorteado na Figura 2?

    \(\boldsymbol\mu(\mathbf{x})\) é a média (e a moda) de \(q(\mathbf{z}\mid\mathbf{x})\), o código "mais provável" da imagem. Decodificá-lo mostra, de forma determinística, o que o código guardou sobre \(\mathbf{x}\). Um \(\mathbf{z} = \boldsymbol\mu + \boldsymbol\sigma\odot\boldsymbol\epsilon\) sorteado soma a isso o ruído da posteriori (\(\sigma \approx 0{,}22\) por dimensão ativa e \(\approx 1\) nas inativas): a reconstrução mudaria a cada execução e misturaria duas coisas, a qualidade da compressão e a incerteza do codificador. No teste, a BCE média é 75,31 nats decodificando \(\boldsymbol\mu\) e 80,75 nats decodificando um \(\mathbf{z}\) sorteado. Para os números do item C, ao contrário, usamos o \(\mathbf{z}\) sorteado, porque o termo de reconstrução da ELBO é uma esperança sob \(q(\mathbf{z}\mid\mathbf{x})\): uma amostra por imagem dá um estimador não enviesado dela. Decodificar \(\boldsymbol\mu\) é a escolha certa para olhar a reconstrução, não para medir a ELBO.

def knn_predict(points, ref, ref_labels, k=15):
    """Rótulo mais frequente entre os k vizinhos mais próximos (distância euclidiana)."""
    out = []
    for pb in torch.as_tensor(points, dtype=torch.float32).split(1000):
        nbr = torch.cdist(pb, ref).topk(k, largest=False).indices        # (B, k)
        votes = torch.zeros(len(pb), 10).scatter_add_(1, ref_labels[nbr],
                                                       torch.ones(len(pb), k))
        out.append(votes.argmax(1))
    return torch.cat(out).numpy()

    2. O que duas dimensões por imagem obrigam o modelo a descartar?

    Com 2 números, o código tem pouca informação a gastar: 6,73 nats por imagem, contra 20,25 com \(d = 16\). Só saber qual dos 10 dígitos é custa \(\ln 10 \approx 2{,}3\) nats, então sobram cerca de 4 nats para todo o resto. O que o modelo descarta é a variação dentro de cada classe: espessura do traço, inclinação, largura, detalhes como a cauda do "9", o alto do "4" aberto ou fechado e as variações de caligrafia. A Figura 5 é a evidência: o plano inteiro é um mapa de identidade do dígito com algumas poucas direções suaves de estilo (por exemplo, a inclinação do "1" no alto e a abertura do "4"), e todas as 225 células são dígitos prototípicos, com espessura praticamente constante e sem nenhum dos traços idiossincráticos da linha de cima da Figura 2. Para quantificar, medimos a variância total de pixels dentro de cada classe (média nas 10 classes) no teste: 41,6 nas imagens reais, 30,8 nas reconstruções do modelo \(d = 16\) (74% preservados) e só 14,0 nas do modelo \(d = 2\) (34%). É essa variação perdida que custa os 52,9 nats a mais de reconstrução, e ela também explica a sobreposição do item 1: um "4" fechado e um "9" diferem justamente num detalhe de estilo que 2 números não conseguem guardar junto com o resto.

    3. Compare as duas linhas da Figura 6.

    A linha latente passa por imagens parecidas com dígitos; a linha dos pixels, não. A interpolação nos pixels é uma soma ponderada de duas imagens: no meio, o "0" e o "1" aparecem juntos, cada um com metade da tinta. A fração de pixels em meia-tinta (\(0{,}1 < x < 0{,}9\)) sobe de 9,4% em \(t = 0\) para 22% a 25% em todo o meio do caminho (\(t = 0{,}11\) a \(0{,}78\)), quando um dígito real tem 8,6%. Isso acontece porque o conjunto das imagens de dígitos não é convexo no espaço dos pixels: ele ocupa uma superfície curva (uma variedade) de dimensão baixa dentro de \([0, 1]^{784}\), e o segmento de reta entre dois pontos dessa superfície sai dela. No espaço latente, o segmento entre \(\boldsymbol\mu_a\) e \(\boldsymbol\mu_b\) é levado pelo decodificador de volta para a superfície: todo \(\mathbf{z}\) é transformado numa imagem com cara de dígito, e o termo de KL empurrou os códigos das imagens de treino para uma região contínua e preenchida em volta da origem, de modo que pontos intermediários do segmento caem perto de códigos que o decodificador já viu. O resultado é uma deformação contínua do formato (o "0" estreita, vira laço e fecha num traço) em vez de um esmaecimento. Não é perfeito: os passos do meio (\(t = 0{,}44\) e \(0{,}56\)) são mais borrados (até 20% de meia-tinta), porque a reta em 16 dimensões atravessa regiões menos densas da posteriori agregada, os mesmos buracos da pergunta 2(a) do Exercício 1.
